# 产品愿景

> 版本：0.1 — 2026-05-21
> 状态：创始团队内部共识文档
> 性质：这不是需求文档，是北极星

---

## 一句话

**我们正在为新的公司架构，建造它的操作系统。**

---

## 我们看到的转变

人类组织运转了几千年，建立在一个不变的假设上：

> **执行工作的，是人。**

所以所有的管理理论、协作工具、组织架构，都是围绕"如何让人更高效地执行"而设计的。Jira 记录人做了什么，Linear 帮人安排做什么，Slack 让人互相告知做什么。

这个假设，在 2024 年开始失效。

Devin 能接到一个 GitHub issue，独立写代码、跑测试、提 PR。Claude Code 能读懂整个代码库，按要求修改、重构、解释。AI agent 能在没有人类参与的情况下，完成过去需要初级工程师三天才能完成的工作。

这不是"更好的工具"。这是**执行者的性质在改变**。

第一次，一个 5 人团队可以做出过去需要 50 人才能做到的事——不是靠每个人工作更努力，而是靠 5 个人指挥几十个 AI agent 并行工作。

这种公司已经存在。它们正在以任何大公司都无法理解的速度移动。

---

## 没有人在解决的问题

现实是：AI agent 能执行，但没有人建造管理它们的基础设施。

团队现在的处境：

把 Devin 接入项目，每次新 session 都要重新解释"我们的代码风格"、"这个模块的设计决策"、"上个月我们决定不做 X 的原因"。

让 Claude Code 提 PR，没有系统决定"这个任务该给人类还是给 AI"，没有结构化的方式验收 AI 的输出，没有统一的视角看"我的团队——包括人类和 AI——今天在做什么"。

**agent 是孤立的**。每个 session 从零开始。团队积累的判断、约定、上下文，在 session 结束时消失。

这是根本性的问题：**所有为团队设计的工具，都假设团队由人组成。**

当团队由人类 + AI agent 混合组成时，没有工具支持这种架构。

---

## 我们在建造什么

**为混合团队设计的操作系统。**

不是在 PM 工具上加 AI 功能。是从头设计一套系统，其中人类和 AI agent 都是第一类团队成员。

**它做什么：**

**1. 统一的 actor 层**
任务可以被分配给人类，也可以被分配给 AI agent。系统根据能力、负载、上下文自动判断谁来做——或者由人类决定。没有区别对待，不区分执行者的性质。

**2. 上下文即基础设施**
每个 AI agent 在接到任务的瞬间，自动获得：这个团队的技术约定、这个项目的历史决策、这个任务的验收标准、过去类似任务踩过的坑。

Agent 不再从零开始。上下文跟着任务走。

**3. 验收协议**
当 AI agent 完成一项工作，系统启动结构化验收：AC checklist 逐条对照、代码规范检查、与团队既有约定的一致性验证。人类只需要做最终判断，不需要重新解释标准。

**4. 持续积累的团队记忆**
每次决策、每次 review、每次发现的问题、每次成功的做法，都沉淀为团队的institutional memory。下一次，任何 agent——无论是人类还是 AI——都能从这份记忆中受益。

**5. 通信平台无关**
Slack、企业微信、飞书、Discord、邮件——系统工作在通信平台之上，不依赖任何一个。团队用什么，它就接入什么。

**6. 持续学习的自主度**
Agent 的可信度从数据中来。成功率越高、验收通过率越高，系统给予的自主度越大。人类的注意力，优先花在最需要判断的地方。

## 我们的用户是谁

**新公司**——用人数衡量很小，用产出衡量很大。

- 创始人直接参与执行、同时指挥 AI agent 的早期团队
- 设计工作室：2 个设计师指挥多个 AI agent 出方案
- 研究团队：3 个研究员指挥 AI agent 做文献综述、数据分析、报告初稿
- 内容团队：策略师指挥 AI agent 写文案、做分析、管理发布日历
- 软件工作室：工程师 review AI agent 写的代码，而不是自己写

他们的共同点：

- 人类专注于**判断、方向、创意、关系**
- AI agent 专注于**执行、检索、生产、迭代**
- 没有传统意义上的"层级"——只有人类和 agent 的协作网络

**他们在哪里**：全球。这不是中国问题，不是技术团队问题，是任何使用 AI agent 的团队的普遍问题。

---

## 为什么是现在

AI agent 的能力在 2024 年跨过了一个阈值。

这个阈值之前：AI 是工具，需要人类逐步指引，不能独立完成一个完整的工作单元。

这个阈值之后：AI agent 能接到一个任务，独立完成，提交可验收的结果。

但管理范式还停留在阈值之前。Jira 不知道任务可以由 AI 执行。Linear 不知道 agent 需要上下文注入。飞书不知道 agent 也需要汇报进度。

**这个 gap 是真实的，是当下的，是有时间窗口的。**

12-24 个月内，Atlassian 会更新 Jira、Linear 会加 agent 支持、微软会在 Teams 里做这件事。那时候，先发优势消失，竞争变成资源战。

现在这件事是空的。

---

## 我们不是什么

❌ **不是 AI 版本的 Jira**
Jira 的问题不是没有 AI，是它的数据模型假设执行者是人。我们从数据模型开始就不同。

❌ **不是企业微信/飞书的竞争对手**
它们是通信平台。我们工作在通信平台之上。我们是协调层，不是通信层。

❌ **不是面向大型企业的**
大型企业有采购流程、IT 政策、组织惰性。我们的用户在大型企业的速度不能容忍他们的地方创业。

❌ **不是 AI agent 框架**
LangChain、AutoGen 是给工程师用的开发框架。我们是给团队用的管理产品。我们不关心 agent 内部怎么实现，只关心 agent 作为团队成员怎么协作。

---

## 成功是什么样的

**第一阶段（12 个月内）**：
一个 5 人团队，通过我们的系统管理 10 个 AI agent 协同工作。每个 agent 在接任务时自动获得完整上下文。人类每天的工作是 review agent 输出，而不是自己执行。团队的产出，相当于过去 30 人的工作量。

**第二阶段（24 个月内）**：
不同规模、不同行业的团队在使用这套系统。系统里沉淀的 institutional memory 成为每个团队无法迁走的资产。新团队成员（人类或 AI）能在几小时内进入完整状态，而不是几周。

**第三阶段（更远）**：
这套系统成为新公司架构的标准配置。就像过去每家公司都需要 OA 系统、ERP 系统，未来每家混合团队都需要一个编排层。我们是最早定义这个品类的人。

---

## 我们相信的事

**人类的稀缺性正在从"执行能力"转移到"判断能力"。**

能写代码的人变多了（因为 AI agent 能写代码）。能决定写什么、为什么写、写完怎么验收的人，仍然稀缺。

我们的系统，是帮助人类把精力集中在他们真正稀缺的地方。

判断、创意、关系、价值取舍——这些不会被 AI 取代。执行、重复、检索、生产——这些正在交给 agent。

**我们在为这种新的分工，建造基础设施。**
