## 2026-05 第六阶段：reviewer / 任务进度架构合并（PR-Agent 风格）

### 背景

前一阶段的 apiQA.js 和 reviewer.js 是两套独立的 LLM 调用：reviewer 在 commit 入仓时跑、apiQA 在晚会时跑，分析的是同一份代码，结论可能打架。借鉴 PR-Agent 的 `TicketCompliance` 设计，把两件事合成一次调用、一份数据源。

### 改动模块

- **`server/services/reviewer.js`** — 重写。输出 schema 新增 `compliance: { taskId, requirements, done, notDone, needsHumanCheck }` 和 `issues: [{ file, startLine, endLine, severity, header, description }]`；`level` 不再由 LLM 直接判定，改为从 issues 派生（critical → Block、security/payment + critical → Escalate、major → Warning）。
- **`server/services/complianceAggregator.js`** — 新增。给定 taskId，取最新带 compliance 的 review 作为快照，返回 `{ done, notDone, needsHumanCheck, progress }`。
- **`server/services/apiQA.js`** — 删除。
- **`server/services/dailyBrief.js`** — `applyEveningReportProgress` 改用 `aggregateTaskCompliance` 算进度；`generateEveningReport` 不再调用 QA。
- **`server/services/githubSync.js`** / **`server/routes/webhookRoutes.js`** — 调 `reviewChange` 前先 `bindActivityToExplicitRefs` 找出关联任务，把 `task` 对象传给 reviewer。
- **`server/store.js`** — migrate 给旧 review 补 `compliance: null` 和 `issues: []`。
- **`src/app.js`** — 任务详情页新增"验收对照"卡片（三列：✅已满足 / ❌未满足 / ⚠️需人工验证）；review 列表展示 compliance badge。
- **`src/styles.css`** — 验收对照卡片样式。

### prompt 设计要点（参考 PR-Agent）

1. **强制复读**：先列出 `ticket_requirements`，再分桶。防 LLM 跳过看不懂的条目。
2. **覆盖完备**：done + notDone + needsHumanCheck 之和必须等于全部验收标准。
3. **非对称报告**：明显 bug 必报；低影响低确信不报；高影响低确信报但标注。
4. **行号锚定**：所有 issues 必须有 file + startLine + endLine + 触发场景，禁止空话。

### 进度新特性：可下降

reviewer 每次都基于"项目当前状态"给全量 compliance，所以新 commit 改坏了旧功能会被识别为"原 done 变 notDone"，任务进度可下降。原 apiQA 用 `Math.max(currentProgress, newProgress)` 永远只涨不降。

### 不受影响的模块

riskEngine、scoring、wecom、stageChecklist、docsManager、assignmentBrief、semanticLinker、standupRoutes、auth — 这些模块不消费 review schema 中变动的字段。

### 数据兼容性

旧 review 自动补 `compliance: null` / `issues: []`，前端遇到 `null` 时显示"尚无 AI 验收数据 — 等待下一次 commit 触发 review"，不报错。

## 2026-05 第五阶段：算法质量改进

### 健康度评分 — 几何平均聚合 + DORA MTTR 维度

核心模块：`server/services/riskEngine.js`（`buildMetrics`）、`src/app.js`（`openHealthModal`）

**问题背景：**

原算法使用线性加权求和（30/30/25/15），任意一个维度极低时，其余维度可以"补偿"拉升总分，导致健康度虚高（例如 7 日零 commit 时总分仍可达 70 分）。

**改进内容：**

1. **聚合函数改为加权几何平均**

   几何平均的关键性质：任意维度趋近 0 时，总分同步趋近 0，无法被其他维度掩盖。

   ```
   健康分 = s_activity^0.25 × s_taskRisk^0.25 × s_reviewClean^0.25 × s_mttr^0.15 × s_standup^0.10
   ```

   对比示例（Commit 活跃度 = 0，其余维度 = 100）：

   | 算法 | 结果 |
   |------|------|
   | 旧：线性加权 | 70 分（虚高） |
   | 新：几何平均 | 0 分（正确反映短板） |

2. **新增 MTTR 维度（DORA 第四指标）**

   计算近 30 日已解决 Block 的平均响应时长，转化为 0-100 分：
   - 0h → 100 分
   - ≥48h → 0 分（线性衰减）
   - 近30日无已解决 Block → 默认满分（100）

3. **权重调整（4 维 → 5 维，对齐 DORA 框架）**

   | 维度 | 旧权重 | 新权重 | DORA 对应 |
   |------|-------|-------|---------|
   | Commit 活跃度 | 30% | 25% | Deployment Frequency |
   | 任务风险 | 30% | 25% | — |
   | Review 清洁度 | 25% | 25% | Change Failure Rate |
   | Block 解决时长 | — | 15%（新增） | MTTR |
   | 站会覆盖率 | 15% | 10% | — |

4. **前端健康度弹窗同步更新**
   - 新增 MTTR 维度展示行
   - 权重数值从硬编码改为动态读取后端 `components[key].weight`（后端改权重前端自动跟）
   - DORA 指标名显示为蓝色标签（`health-dora-tag`）
   - 说明文字从"分桶加权"更新为"DORA 对齐几何平均"

**注意：** 权重本身（0.25/0.25/0.25/0.15/0.10）仍为经验设定，DORA/SPACE 论文不提供通用权重系数。建议团队运行一段时间后根据实际感知调整，或改用等权重（各 20%）。

## 2026-05 第四阶段：任务进度智能评估

### API QA 自动评估（方案 A）

晚会流程新增 AI 驱动的任务完成度评估，替代原来「有 commit 就 +12%」的粗糙逻辑。

核心模块：`server/services/apiQA.js`

**执行流程（每个任务 3 个 checkpoint）：**

1. `[1/3] 生成测试用例`：Claude 读取任务验收标准，生成 0-3 个只读 GET 测试用例（路径以 `/api/` 开头）；无法通过 API 验证的任务（UI 交互、部署配置）返回空数组
2. `[2/3] 执行 API 测试`：服务端自调用本机接口，5 秒超时，记录每条请求的状态码和响应摘要
3. `[3/3] 评估完成度`：Claude 综合测试结果、commit 数量、Block 审阅数和验收标准，输出建议进度（0-100）、理由和置信度

**批量策略：** 每次晚会最多评估 5 个有 commit 且有验收标准的任务，并发执行，单任务失败不影响其他任务。

**进度写入规则（`applyEveningReportProgress`）：**

| 情况 | 进度 | signal |
|------|------|--------|
| QA 成功 | 取 `max(当前, 建议值)` | `AI 评估进度 X%（原因）` |
| QA 失败（LLM/网络错误） | 不变 | `QA 评估失败（原因），进度待人工确认` |
| 未参与本轮评估（无验收标准等） | 不变 | `QA 未运行，进度待人工确认` |

原来的固定 +12 逻辑已删除，不再有无声的兜底。

**错误可见性：** 每步失败均 throw 并在调用层记录到 PM2 日志，批量层打印整体通过率。

## 2026-05 第三阶段：企业微信写入工具

### 新增三个企微写入接口

企微插件不知道内部 taskId，所有写接口均支持按任务标题关键词模糊匹配。

- 工具名：`getWeComTasks`
- 路径：`GET /api/wecom/tasks`
- 输入参数：无
- 输出参数：`summary`（String）

#### `POST /api/wecom/claim` — 认领任务

输入参数：

| 参数 | 类型 | 说明 |
|------|------|------|
| `owner` | String | 认领人姓名，如 `田家铭` |
| `taskKeyword` | String | 任务标题关键词，如 `TRTC` |

输出参数：`result: String`（操作结果，含 ✅ / ❌ 提示）

企微工具配置：
- 工具名：`weComClaimTask`
- 路径：`POST /api/wecom/claim`
- 请求头：`X-CUE-API-Key: <CUE_API_KEY>`（若配置了 key）
- 输出参数：`result`（String）

#### `POST /api/wecom/standup` — 提交站会

输入参数：

| 参数 | 类型 | 说明 |
|------|------|------|

| `yesterday` | String | 昨日完成 |
| `today` | String | 今日计划 |
| `blockers` | String | 阻塞项（可留空，默认"无"） |

输出参数：`result: String`

企微工具配置：
- 工具名：`weComSubmitStandup`
- 路径：`POST /api/wecom/standup`
- 请求头：`X-CUE-API-Key: <CUE_API_KEY>`

输入参数：

| 参数 | 类型 | 说明 |
|------|------|------|

企微工具配置：
- 工具名：`weComUpdateProgress`
- 路径：`POST /api/wecom/progress`
- 请求头：`X-CUE-API-Key: <CUE_API_KEY>`

### 8. 晚会闭环

会前：同步 Cue.AI GitHub commit → 扫描 AI Review 风险 → 对照前一天任务领取和今日 commit → 生成会前报告 → 生成下一步细化目标

会中：成员领取任务 → 登记今日计划 → 登记阻塞项 → 记录站会信息

会后：生成会后总结 → 更新任务进度 → 更新阶段进度 → 输出计划调整建议 → 推送企业微信

## 技术约定

### LLM 调用
- 统一入口：`callClaude(systemPrompt, userPrompt)` → 文本或 `null`
- System prompt 固定（不含日期/用户输入），保持 prompt cache 有效
- 每个调用方必须处理 `null` 并降级
- 不要把会变化的内容（日期、用户输入）放进 system prompt，否则破坏缓存

### 路由
- `server/index.js` 的 `handleApi` 是顺序 if-else 链，路由定义顺序即优先级
- 新增路由前确认没有同路径的重复定义（历史上曾出现 POST `/api/reports/evening` 重复定义）

### 时区
- 所有日期操作用 `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Shanghai' })`
- 不使用 `new Date().toISOString().slice(0, 10)`（UTC 会差一天）

### AI Review 级别
- 固定四级：`Pass` / `Warning` / `Block` / `Escalate`
- LLM 输出经 `normalizeLevel()` 规范化（含中文映射），不能直接使用 `result.level`
- 只有 Block / Escalate 需要人工介入，计入 `pendingReviews`
- P1 硬风险不能被 LLM 降级

## Cue.AI 提交规范

所有 Cue.AI 仓库统一遵守（完整规则见 `.github/CUE_AI_GITHUB_RULES.md`）：

1. 每个任务必须先有明确目标、负责人、截止时间和验收标准
2. 每个分支必须对应一个任务或明确的修复目标
3. 每个 commit 标题必须使用规范前缀：`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:` / `merge:`
4. commit 标题必须说明业务或技术意图，不能只写 `update`、`fix bug`、`changes`
5. 涉及功能开发、接口变更、权限、认证、支付、数据结构、部署配置的提交，必须关联任务、issue、PR 或阶段目标
6. 单个 PR 尽量聚焦一个目标；超过 500 行核心变更时优先拆分
7. 高风险模块必须补充测试说明或人工审阅说明
8. 不能提交密钥、token、密码、私有证书、真实用户隐私数据
9. PR 合并前必须通过 AI Review；Block 级问题必须先处理或由负责人明确豁免
10. 站会、请假、延期和阻塞必须在项目中枢中留下可追踪记录

## 第八阶段：稳定性修复 + Webhook 实时同步（2026-05-21）

### Token 烧光 bug 修复

**根因**：`upsertPullIntoStore` 对每次同步的每条 PR 都无条件调用 LLM，10 分钟轮询 × 31 条 PR × 多标签页 = 3014 次调用 / 1 小时，烧光 ¥15。

**修复**：加入 `unchanged` 跳过判断——PR 的 `state` 和 `updatedAt` 未变化且已有 `hubReview` 时跳过 LLM，只对真正变化的 PR 触发 review。

**调试工具**（保留生产）：
- `server/services/syncTrace.js`：append-only 调用追踪日志，`GET /api/debug/sync-trace` 查看
- `LLM_DRY_RUN=true` 环境变量：拦截所有 LLM 调用走 stub，用于排查调用频次不烧钱

### Webhook 驱动 PR 实时同步

**替代 10 分钟批量轮询**：目标仓库（Cue.AI）GitHub Webhook 发送 `pull_request` 事件 → Hub `/api/webhooks/github` → `upsertPullFromWebhook` 单条实时 upsert。

**关键变更**：
- `pullPipeline.js` 新增 `upsertPullFromWebhook`（动态 import store 避免循环依赖）
- `webhookRoutes.js` 接入 `pull_request` 事件，fire-and-forget 调用
- `index.js` 注册 `upsertPullFromWebhook`
- 批量轮询降频至 60 分钟（`GITHUB_SYNC_INTERVAL_MINUTES=60`）作安全兜底

**验证**：目标仓库 PR 事件触发后 Hub 日志出现 `PR #N (action) upserted via webhook`，延迟从 10 分钟降至秒级。

### PR-Agent 激活

目标仓库（CUEAITECH/Cue.AI）配置 GitHub Actions PR-Agent workflow，充值 ikuncode.cc 后正常工作，`/review` 评论返回完整 PR Reviewer Guide。
