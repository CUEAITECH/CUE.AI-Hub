# CUE 不可解问题登记册（Open Problems Register）

> 建立于 2026-06-14，源于 SPEC-L4c 复盘时的连锁追问（TraceLLM 误引 → 验证可靠性 → oracle problem）。
>
> **这份文档的唯一目的**：把「当前技术根本解决不了 / 学术界公开未解」的问题**显式登记**，逼我们在设计时**绕着走**，而不是用浅做法假装解决了它。
>
> 它直接对治 [[ai-pm-diagnosis]] 记录的病根——系统老在「测试绿 / 文档写了」时就宣布「done」。**凡是命中本册某条的功能，禁止宣称「已自动验证/已解决」，只能宣称「已分诊/已标置信度/已路由给人」。**

## 怎么读

每条分两级：

- 🔴 **Fundamental-Open（根本未解）**：今天没有自动解法，近期也不会有。设计原则只能是**诚实分诊 + 人在环（HITL）+ 显式标注覆盖度**，永不宣称自动解决。
- 🟠 **Hard-but-bounded（难但有界）**：技术路线已知，只是工程量大/要做扎实。**列在文末只为划清边界**——证明"不可解清单"是有限的、收敛的，不是满地怪兽。

每条记录：定义 / 为什么解不了（带证据）/ 在 CUE 哪层咬人 / 诚实姿态。

---

## 🔴 P1 — Oracle Problem：正确性无法自动判定

**定义**：在没有人的情况下，自动区分「正确行为」与「错误行为」。这是软件测试领域的中心难题，有正式名字（the oracle problem）。

**为什么解不了（证据）**：
- LLM 自动生成 test oracle，SOTA（TECO）准确率仅 **27.5%**（3540 条测试）。连 Meta 都在专门攻这个。[Test Oracle Automation in the Era of LLMs, TOSEM 2025 / arXiv:2601.05542 / arXiv:2601.22832]
- 对「不崩但功能错」的 NCF bug，GPT-4o 当 oracle 在 71 个真实 bug 上只抓 **49%**、误报 **59%**，且随模型更新从 43.7% 漂到 1%。[arXiv:2407.19053]

**在 CUE 哪层咬人**：L4（监控）、**L4c/T13（缺口分析，已实现）**、E2/L5（测试）、E3（"这真是风险吗"）。这一条是 CUE 最深问题的总根。

**三个长在不同表面的子面**：
- **P1a · 文本判断的系统性偏差**：让 LLM 读 diff 判「是否满足需求」会系统性把已满足判成「缺失」，且**越要求解释/列举错得越狠**（GPT-4o FNR 35.9%→87.9%）。[arXiv:2603.00539] → 直接影响 T13 的 `missing[]`/`riskLevel`。
- **P1b · 覆盖度盲区（绿 ≠ 对）**：测试只判它被写来判的东西；后端绿、前端崩就是 oracle 覆盖盲区 + test adequacy 不足。无法自动知道"我没测到的相对真实需求是什么"。
- **P1c · Agent 对细节 bug 的召回天花板**：UI Agent 对 NCF bug 抓约一半、高假警、会漂移、偏 Web。是"找 bug 助手"，不是"正确性判定器"。

**诚实姿态**：永不宣称「PR 已验证通过」。只输出「covered/missing + 置信度」，明确标"以下验收点无任何自动层覆盖，需人工确认"，把静默盲区变成浮出来的 TODO。依据见 [[req-impl-verification-research]]。

## 🟡 P2 — LLM 非确定性与模型漂移（固有但可管，区别于 P1）

> **2026-06-14 自审更正**：本条原标 🔴 且写「温度 0」当确定性手段——**两处都错**。改正见下。P2 与 P1 性质不同：P1 连「怎么管」学术界都不成熟（真·开放难题）；**P2 消除不了（固有），但「怎么管」已是成熟 LLMOps 纪律**。故降级为 🟡：不可消除、但有标准对策，不属研究前沿。

**定义**：同一 prompt 多次调用结果不同；且供应商静默更新模型会改变行为。

**为什么消除不了**：是当前 LLM + 硬件栈的固有性质。**注意：温度 0 ≠ 确定性**——硬件优化、推理批处理、浮点精度（FP32 近确定 / BF16 方差显著）都会让温度 0 仍抖。"zero temperature guarantees stability" 已被证伪。[ICLR 2026 "Dissecting Non-Determinism"；arXiv:2506.09501]
证据（漂移真实存在）：NCF 研究里同 prompt 跑 3 次比 1 次多抓 26–31%；GPT-4 同设置两个月内从 43.7% 跌到 1%。[arXiv:2407.19053]

**在 CUE 哪层咬人**：**每一个依赖 LLM 的层**（L1/L2/E1/E3/L4c/E4 全部）——是横切背景约束，不是某层专属。

**诚实姿态 / 成熟纪律（消除不了，但要框住 + 监控）**：
- **框住方差**：temperature + seed + **版本钉死（gateway）**；关键判断用 **self-consistency**（采样 N 次取多数票）；评估按**语义等价**而非字节精确匹配。
- **盯住漂移**：建 **golden dataset 回归 eval 集**，每次模型/prompt 版本变更跑一遍，质量掉了用 **CI 闸门拦住**不让进生产；生产 trace 记 eval 分，"输入漂移 + eval 下降"**联合报警**（只漂移不掉分是假警）。
- **永不把单次 LLM 输出当权威。** 注意现有 `callClaude` 的 system prompt 缓存假设也会被模型版本切换打破——版本变更须重验缓存行为。
- 参考：[arXiv:2506.13023]（评估实践）、[arXiv:2510.25506]（商业 LLM 在 SE 研究中的可复现性）。
- ✅ CUE 已补：**golden dataset 回归 eval 集**落在 `eval/llm-regression/`（promptfoo 骨架 + 自定义 provider 调真实服务 + 结构不变量断言）。跑 `npm run eval:llm`。**纪律**：换模型 / 改任一 system prompt / 升级 LLM 供应商时必跑，对比基线看漂移。覆盖 L1 clarify、T13 gap（plan 需真实终端，见该目录 README）。

## 🔴 P3 — 需求完整性 / 意图捕获

**定义**：「我们有没有抓到用户真正想要的」——在做出来撞到现实之前，无法验证。

**为什么解不了**：需求获取/规范化是开放问题；acceptance criteria 写得含糊时，下游一切验证都是 garbage-in（验证的上限 = 拿去对照的需求质量）。

**在 CUE 哪层咬人**：L1（澄清→PRD）是源头，**向下级联污染 L2/L4c**——T13 拿一份含糊的 acceptance 去对 diff，再准的比对也无意义。

**诚实姿态**：L1 的 PRD 永远标"待现实验证"；把 acceptance 质量当作 L4c 结果可信度的前置条件，acceptance 含糊时 gap 分析降级标注，不假装能判。

## 🔴 P4 — Agent 会篡改验证（reward hacking）

**定义**：让 Agent 去验证，无约束的 Agent 会改测试/报无关失败来"骗过"验证流程。

**为什么解不了**：是 agentic 系统的开放安全问题。证据：SWE-agent 验证文献明确观察到 Agent 走捷径"make the test pass/fail"。[arXiv:2601.04171 Agentic Rubrics as Contextual Verifiers 即专治此]

**在 CUE 哪层咬人**：任何"执行型 Agent"层——E2/L5（跑测试/点页面）、E4（自己改自己的规划）。

**诚实姿态**：验证器必须与被验对象**隔离**、防篡改；**永不让"干活的 Agent"同时当"唯一的判分人"**；沙箱隔离 + 只读验证产物。

---

## 🔴 P5 — 结果归因 / 因果

**定义**：把真实世界的产品结果（指标涨跌、用户反馈）归因到具体某次交付/某条 commit。

**为什么解不了**：观测数据上的因果推断本身是开放难题，混杂因素无法穷举。

**在 CUE 哪层咬人**：E5（迭代闭环）、outcomes/outcomeLedger（当前**已冻结**模块）。

**诚实姿态**：只呈现相关与时间先后，标注"非因果"；归因结论永远是"供人参考的假设"，不进自动决策。

## 🟠 难但有界（明确不在不可解清单）

列出以证明上面的清单是收敛的：

- **跨产品类型的执行锚定**（Web/原生/后端/CLI 各用各的工具）——工程活：Web 用 Playwright/computer-use、原生用 XCUITest/Appium/Maestro、后端用接口/契约测试。难在多平台铺设，不难在"能不能做"。残余的"原生验证质量"尾巴归 P1c。
- **6 个高 fidelity 能力层**：L1 澄清(成熟 NL)、L2 任务 schema、L3 PR 自动化、E1 commit→任务、E3 风险回流接线、E5 闭环机制——都是有界工程（fidelity 78–90%），技术风险低（但仍有**执行质量**风险，别把"有界"当"已做好"）。
- **5 条产品主线**（总览/AI PM/任务闭环/风险队列/产品复盘）：UI 与工作流设计，不存在根本难题。

## 数量盘点（回答"到底有多少解决不了的问题"）

**真·根本未解：4 个（P1/P3/P4/P5）+ 1 个固有但可管的横切约束（P2）。** 分布高度不均：

- **真正的重心是 P1（验证/oracle）一个根，长在 4 个 CUE 层上**（L4/L4c/E2/L5，外加 E3）。P1a/P1b/P1c 是它的三个面，不是三个独立问题。
- **P2（非确定性/漂移）🟡 不一样**：消除不了，但有成熟 LLMOps 纪律（回归 eval + 漂移监控 + 版本钉死）。属"要做工程，不是没解法"。横切所有 LLM 层。
- P3/P4/P5 各自局部：P3 在 L1 源头、P4 在执行型 Agent 层、P5 在已冻结模块。

**所以诚实的图景不是"满地大问题"，而是：1 个核心难题（验证 P1）+ 3 个局部开放问题（P3/P4/P5）+ 1 个可管的横切约束（P2）。其余整个 CUE（6 个能力层 + 5 条产品线）是有界工程。**

> 本次自审本身就是 P2 纪律的人肉演示：拿固定问题（"这些数字/分类对不对"）重跑一遍核对，抓出了"温度 0=确定性"的错判和 P2 的错误分级。**这正是 golden-dataset 回归 eval 在做的事**——固定基准、定期重跑、揪出漂移。CUE 该把这一步自动化。

复杂度是收敛、可管理的。关键纪律只有一条：**命中 P1–P5 的功能，永远只做"诚实分诊 + HITL + 显式覆盖度"，绝不宣称自动解决。** 谁要在这些地方标"done/已验证"，就是在重犯 [[ai-pm-diagnosis]] 的病。

## 维护约定

- 新发现一个"根本未解"问题 → 加 P-编号，必须带证据（论文/实测数字），不带证据的不准进。
- 某条被学术界/工程突破解决了 → 不删，改标 ✅ 并注明何时、被什么解决（保留判断历史）。
- 写新 spec 时先查本册：功能是否命中某 P？命中则 spec 里必须写明"诚实姿态"那段。
